| Critical | `u_encoders.c:69` | `clear_both_encoders_count()` clears encoder A twice and never clears encoder B. |

## Improve naming and consistency

Names currently make the control logic harder to review:

- `p_manouver_controler` → `maneuver_controller_update`
- `p_line_controler` → `line_controller_update`
- `manouver_ended` → `maneuver_end`
- `RS_DATA_TABLE_SIZE` → `LINE_SENSOR_COUNT`
- `pwm_real_A` → `motor_a_pwm`
- `goal_steps_A` → `target_steps_a`
- `p_manouver_controler_enabled_flag` → `maneuver_controller_enabled`

There are also spelling inconsistencies such as `manouver`, `controler`, and `funckji`. In embedded control code, descriptive names are more valuable than short names because the behavior is stateful and mathematical.

Use a consistent convention, for example:

```c
static bool line_controller_enabled;
static bool maneuver_controller_enabled;
static int motor_a_pwm;
static int motor_b_pwm;
```

Since these are flags, use `bool` rather than `int`.

## Replace scattered flags with an explicit state machine

Currently behavior is controlled through several independent flags:

```c
p_line_controler_enabled_flag
junction_detection_enabled_flag
p_manouver_controler_enabled_flag
step_check_enabled_flag
```

This permits invalid combinations. For example, multiple controllers could accidentally be enabled or disabled inconsistently.

Use one state instead:

```c
typedef enum {
    CONTROL_STATE_LINE_FOLLOWING,
    CONTROL_STATE_FORWARD_MANEUVER,
    CONTROL_STATE_TURNING,
    CONTROL_STATE_STOPPED
} control_state_t;
```

Then the main loop can dispatch behavior based on one value. This makes transitions such as “turn finished, resume line following” explicit.

## Separate calculation from hardware effects

Functions like `p_line_controler()` both calculate control output and mutate global motor state. That makes them difficult to test.

Prefer pure calculations:

```c
typedef struct {
    int motor_a;
    int motor_b;
} motor_command_t;

motor_command_t calculate_line_control(const int *sensor_values);
```

Then apply the result separately:

```c
motor_command_t command = calculate_line_control(sensor_values);
set_motors_duty(command.motor_a, command.motor_b);
```

This would let you test controller math on a normal computer without an ESP32, motors, ADC, or encoders.

Several calls ignore error results:

- `adc_oneshot_read()`
- `adc_cali_raw_to_voltage()`
- `pcnt_unit_get_count()`
- `pcnt_unit_clear_count()`
- `ledc_set_duty()`
- `ledc_update_duty()`

You already use `ESP_ERROR_CHECK()` during initialization. Apply a consistent policy during runtime too:

```c
esp_err_t err = adc_oneshot_read(handle, channel, &raw);
if (err != ESP_OK) {
    ESP_LOGE(TAG, "ADC read failed: %s", esp_err_to_name(err));
```

Avoid silently continuing with uninitialized or stale sensor values.

For public functions, consider returning `esp_err_t` where failure is possible:

```c
esp_err_t get_battery_voltage_mv(int *voltage_mv);
```

## Add bounds and overflow protection

The controller uses unconstrained arithmetic:

```c
p_result = ...
pwm_real_A = PWM_BASE_VALUE + p_result;
pwm_real_B = PWM_BASE_VALUE - p_result;
```

Clamp the control output before sending it to the motor driver. Also consider using `int32_t` or `int64_t` for intermediate calculations involving degrees, wheel circumference, and encoder counts.

A reusable helper would be useful:

```c
static int clamp_int(int value, int min_value, int max_value);
```

Use it both in the controller and motor layer.

## Improve the main loop structure

`main.c:38` contains one infinite loop with hard-coded behavior:

```c
turn(90);
while (true)
```

Consider moving control-loop logic into a named task:

```c
static void control_task(void *arg);
```

Then define the update frequency explicitly, preferably with `vTaskDelayUntil()` rather than repeated `vTaskDelay()`:

```c
TickType_t last_wake = xTaskGetTickCount();

for (;;) {
    control_update();
    vTaskDelayUntil(&last_wake, pdMS_TO_TICKS(10));
}
```

This gives you a more stable 100 Hz control loop.

Also, code after the infinite loop is unreachable, including the battery debug call at `main.c:50`.

## Use logging instead of raw `printf`

Use ESP-IDF logging:

```c
static const char *TAG = "control";

ESP_LOGI(TAG, "maneuver complete");
ESP_LOGW(TAG, "encoder target not reached");
ESP_LOGE(TAG, "ADC read failed");
```

This gives you log levels, module names, and better filtering than raw `printf()`.

Avoid frequent logging inside the 10 ms control loop unless it is rate-limited; serial output can disturb timing.

## Make configuration centralized

Constants are spread across modules:

- GPIO assignments
- PWM frequency
- sensor thresholds
- controller gains
- wheel geometry
- encoder limits

Create a configuration header or use Kconfig/project configuration for values that are likely to change during calibration. For example:

```c
#define CONTROL_LOOP_PERIOD_MS 10
#define LINE_SENSOR_THRESHOLD_MV 2000
#define LINE_CONTROLLER_BASE_PWM 200
```

Prefer names that include units. `MAX_RS_ERROR_VAL_P_CONTROLER` is difficult to interpret, while `LINE_ERROR_MAX_MV` is clearer.


Then fix warnings rather than suppressing them. Warnings would likely help detect:

Also adopt `clang-format` and format all C files consistently. Consistent formatting makes logic errors easier to spot in reviews.

## Be careful with `volatile`

The controller uses several `volatile static int` flags. `volatile` does not make access atomic or thread-safe. It only tells the compiler not to optimize away reads and writes.

If the values are only accessed from one task, remove `volatile`. If they are shared between tasks or interrupt handlers, use:

- FreeRTOS mutexes
- critical sections
- task notifications
- atomics where appropriate

Document which task owns the control state.
